# YeonBriefs — 给珱垣的版本简报

> **用途**：珱垣撰写 `README.md`「当前状态」、`YeonPlans/` 方案文档与 GitHub Release 正文的素材来源。
> **读者**：珱垣（产品 / 宣传口径决策者）。
> **维护者**：AI（工程侧）。

---

## 一、目录定位

项目版本文档分三层，读者与用途各不相同，各写各的、互不代笔：

| 文档 | 读者 | 内容性质 | 维护者 |
| --- | --- | --- | --- |
| [`README.md`](AI生成的sakumanga%20README.md) | 用户 | 对外展示、卖点、使用方式 | **珱垣**（AI 不写） |
| `DSPlans/YeonBriefs/BRIEF_vX.Y.Z.md` | 珱垣 | **精炼事实素材**（本目录） | AI |
| [`CHANGELOG.md`](../../CHANGELOG.md) | 开发者 / 想纵览演进的人 | 跨版本一览 | AI |
| `DSPlans/VerNotes/RELEASE_NOTES_vX.Y.Z.md` | 开发者 / 愿意看细节的人 | 单版本详述（技术口径、升级说明、已知问题） | AI |

GitHub Release 正文 = 珱垣基于本目录简报自行撰写，AI 不代笔。

---

## 二、文件命名

`BRIEF_vX.Y.Z.md`，**一个版本一份**，与 `VerNotes/RELEASE_NOTES_vX.Y.Z.md` 保持同一版本号后缀。

---

## 三、写入时机

1. **每个 Round 完成**：在对应版本文件末尾追加一节 `## Round NN · <主题>`，只写事实——做了什么、影响谁、有无升级影响，1~3 条即可。跟随该 Round 收尾的 `docs` 提交一起入库。
2. **发版时**：把增量节组装成定稿结构（版本信息 / 主题候选 / 亮点 / 升级注意 / 已知问题 / README 待改点 / 机械清单），并主动通知珱垣「可以发版了」，附简报路径。

---

## 四、写作口径

- **只陈述事实，不写宣传话术**——卖点措辞由珱垣决定。
- 每条一句话，说明「用户能感知到什么」，避免纯实现细节词汇（函数名、字段名），除非它影响升级。
- 「已知问题」如实写，即使不利于宣传——供珱垣判断是否对外提及。
- **不代写 README 正文**，只指出「哪一段需要改 + 要点」。
- 版本号规则：MINOR 含新功能（如 2.3.0），PATCH 仅修 Bug（如 2.2.x）；**未发布的版本号若被后续内容吸收，不单独发版**。

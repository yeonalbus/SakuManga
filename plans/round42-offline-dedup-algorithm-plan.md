# Round42：离线查重（疑似重复）算法升级方案

> 起因：离线「本地书库维护 → 疑似重复」漏检。用户报告 `gid 4178996` / `gid 4196371`
> （`[夢ねこ屋 (むーにゃん)] 極東絢爛賭博島ドリームアイランド3 アルトリア&頼光編 …`，卡片显示名相同、
> 仅汉化组标记不同）未被报为疑似重复，且确认「其他还有类似情况」。
>
> 诊断结论（实测）：名称级指纹**只在 `title` 字段上做正则清洗**，存在三层缺陷，
> 在 3575 本维护候选集上现有实现只产出 **10 簇**，而按卡片显示标题归一应有 **51 组**
> （8 组已覆盖 + **43 组完全漏检**，漏检率 ~84%）。
>
> 本文件为决策与设计落盘（Part A：诊断 + 决策 + 方案）。实施前如无新增证据，按此执行。

## 一、诊断结论（实测）

诊断口径：云端生产库快照（`Y:\SakuManga\manga.db`），维护候选集 = `source=offline` 且未老化、未移除
（4095 → 排除 516 老化 + 4 已移除 = **3575 本**），与 `filterOfflineUpdateEnabled` 同口径；
用同一份代码在本地复现聚类（`detectTitleClusters`）。

### 1.1 漏检规模

| 口径 | 结果 |
| --- | --- |
| 现有实现产出 | **10 簇** |
| 按「卡片显示名（`titleJpn \|\| title`）」激进归一应有 | 8 组已覆盖 + **43 组完全漏检** |
| 用户报告的两本 | ✅ 落在「完全漏检」组内（`aged=0 / removed=0 / scan_path_id 空` → 正常参与候选，非被过滤） |

### 1.2 三层根因（`backend/internal/services/dedup_title.go`）

| # | 层 | 问题 | 实测证据 |
| --- | --- | --- | --- |
| R1 | 字段池 | `detectTitleClusters` 调 `fingerprintTitle(c.Title, artist)`，**只吃 `title`**（metadata 里常为罗马音/英文），完全不吃 `titleJpn`（卡片展示的日文原名） | 显示名完全一致却漏检的 3 组；`title` 为日文的条目与 `title` 为罗马音的条目核心名永不相交 |
| R2 | 词表/括号形式 | `reVersionTokens` 的英文与版本类 token **一律要求圆括号包裹**（如 `\((?:…\|無修正\|…)\)`），而 E 站命名大量用方括号；中文词表缺 `中国翻訳`/`中国語`；汉化组正则只认含「汉化组」三字的 token | `[無修正]` 影响 **17 组**、`[中国翻訳]` 影响 **11 组**；用户两本走 `title` 时核心名残留 `[空気系☆ ]` vs `[黎欧出资 ]` |
| R3 | 剥离残留 | `dl\s*版` 为无括号剥离 → `[DL版]` 被剥成 `[ ]` 空方括号残留 | 两本即使改用 `titleJpn` 仍不合并：`…[中国翻訳] [ ]` vs `…[中国翻訳]`（差一个 `" [ ]"`） |

**根因分类（43 组）**：仅清洗层 25 / 字段+清洗 15 / 仅字段 3 / 其它 0；其中「显示名完全一致」3 组。
（key 是唯一门槛：`buildCluster` 只用页数差决定置信度，不阻断成组 → key 分裂即永不报警。）

### 1.3 关键认知：`title_jpn` 是规范标题

E 站维护的 `title_jpn` 对同一作品的不同上传/汉化版几乎完全一致（只差 `[DL版]`/`[無修正]`），
而 `title`（罗马音）带汉化组标注、是脏字段。

→ **结论：把规范字段（`title_jpn` + `artist` tag）当主键，正则清洗只作兜底**；
不要在脏字段上继续堆正则。

### 1.4 反直觉实测：内容指纹余量不足（故本轮不做）

对真实漫画页做感知哈希（每本抽 12 页，跨页最近邻，64-bit pHash）：

| 对照组 | 关系 | pHash 最近邻均值 | ≤10 命中率 |
| --- | --- | --- | --- |
| 同一文件两次入库（無修正 vs DL版） | 完全相同内容 | **0.8** | 100% |
| 用户报告的两本（同作品·不同汉化版） | 目标正样本 | 10.8 | 58% |
| 同系列·不同卷 | 应判不同 | 15.2 | 25% |
| 完全不同作品 | 应判不同 | 17.8 | 8% |

正样本（10.8）与「不同卷」（15.2）仅约 4 bit 余量 → **整页 pHash 不能做主判据**；
要可用需分块感知哈希/特征点匹配等更重方案（见 D1）。

### 1.5 作者标识信号实测（circle 兜底的依据）

用户提出「E 站规范命名里 `[中括号]` 就是画师名」——实测**基本成立，但有一个关键细节**：

| 指标 | 实测值（3575 本候选集） |
| --- | --- |
| 显示名以 `[` 开头（含社团/画师段） | **2932 本（82.0%）** |
| ↳ 形如 `[社团 (画师)]` | 1014（34.6%） |
| ↳ 形如 `[画师]` / `[社团]` 纯名 | 1918（65.4%） |
| `artist` tag 非空 | **3297 本（92.2%）** |
| `artist` tag 为空 | 278 本（7.8%） |
| ↳ 其中**有开头中括号可兜底** | **218 本** |
| 两者都缺（无 tag 也无开头括号） | 60 本 |

**关键细节**：`[社团 (画师)]` 括注里是**日文名**（`むーにゃん`），而 `artist` tag 是**罗马音**（`muunyan`）→ 直接字符串比较 **89% 不匹配**（一致 105 / 不一致 866）。

→ 因此 circle 的正确用法是「**不同则否决**」，**不能**「相同则加分」；且必须 **artist 优先**：
- 同一 `artist` 对应多个 circle 名的情况有 **101 个**（同画师多社团）→ 用 circle 差异做硬否决会漏报，
  所以只有「artist 缺失」时才启用 circle 兜底；
- 同一 circle 名对应多个 `artist` 的有 **18 个**（同名社团）→ circle 相同不能推断同作者。

## 三、决策记录（Round42 已与用户对齐）

| # | 决策 | 说明 |
| --- | --- | --- |
| D1 | **不做内容抽页**（取消 Tier 3） | 不读漫画文件、不引入 OpenCV 绑定/Python 侧车。代价：判重证据仅剩元数据，**「标题完全不同且无 gid 关系、页数也不同」的同类作品抓不到**。备注：未来若要做，纯 Go 分块感知哈希用 `golang.org/x/image` 即可，**无需 OpenCV** |
| D2 | 联网复核做成**设置项，默认关闭** | 开启后仅对 Tier 2 未决候选，用 `title_jpn` + `artist` 走 E 站反查；复用 `ehRateLimiter` 限流；结果缓存进 DB |
| D3 | 判重范围 = SakuManga 两个来源 | `Z:\SakuHentai\Comics`（下载导入，`scan_path_id` 空）+ `Z:\Comics`（额外扫描路径）；范围沿用「离线维护」开关。**不读** LANraragi（`Z:\Ehentai`）/ Komga（`Z:\Komga`） |
| D4 | 性能预算：增量 **≤5 分钟**（10 分钟极限）；全量不设限 | 增量的目的是「快速确认这批新下载是否有重复」 |
| D5 | 交互优先级：**后台跑不占人 > 进度反馈 > 总耗时** | 用户搜刮完就要看结果；进度必须可见（避免"看不到进度而焦虑"） |
| D6 | 接受**结果持久化到 DB** + **判重与联网核对解耦** | 现状缓存仅在内存，重启即丢、必须重扫 |
| D7 | **不做自动定时维护** | 引入数据库时全量一次，之后增量即可 |
| D8 | **忽略表 key 迁移必做** | 否则算法升级后用户已忽略的组会全部「复活」 |
| D9 | 标定集：**自动构造候选 + 用户抽查确认** | 产出对照表（gid 对 + 判据 + 建议），用户只需回复判错行；同时留作回归用例 |
| D10 | **作者硬否决（不可协商）** | 判定作者**只认 `artist` tag**：双方非空且不等 → 绝不判重复；**artist 缺失时不否决**（部分版权本/商业志有意不带 tag），改用「核心名+卷号」兜底合并但降档标注。实测「circle 名不同 + artist 缺失」的分歧区全库仅 1 对，且该对实际是同一作品（命名把汉化组放到开头，导致 circle 提取抓错）→ 故 **circle 名只作展示辅助，不参与自动否决**。依据：用户标注「不同作者的同名画廊」必须避免（样本 `1269349`/`2806799`、`3869341`/`3259663`、`3611722`/`4147627`，三者 artist tag 均不同） |
| D11 | **误报分级标准** | 只有「不同作者同名」不可接受；「同作者同名但不同画廊 / 同作品不同上传内容 / E 站命名之外」的误报**可接受** → Tier 2 阈值可据此放宽，优先保召回 |
| D12 | 同作者同名但**不同语言 / 有修与无修 / 动态与静态** | **按重复处理**（用户可能确实要保留多个版本）→ 无需按 `language:` tag 拆分，也不因 `[無修正]`/`Animated` 差异降档 |

## 四、设计方案：分层判重

```
Tier 0  强证据 · 确定性（现有规则 1/2/4，保留）
        file_hash / 目录内容签名 / 同 gid / parent 链
Tier 1  规范键 · 决定性（本轮落地）
        硬约束 = author_rel ≠ diff（D10，先过闸）
        主键   = normalize(title_jpn) + artist(tag) + 卷号
        清洗   = 方括号版本标记词表 + 汉化组 + 空括号残留 + 双字段池兜底
Tier 2  概率打分 · blocking + scoring（本轮落地）
        blocking：author_rel ≠ diff + 同卷号 + 页数差 ≤5 + 核心名 token 有交集
        scoring ：title_jpn 相似度 + title 相似度 + tag Jaccard + 页数比 + 文件大小比 → 加权总分
        分档    ：high / medium / low（low 折叠，不打扰）；作者未知（无 tag 且无 circle）时整体降一档
Tier 3  内容指纹（不做，见 D1；留存为未来可选项）
```

### 4.1 Tier 1（确定性层）

- `fingerprintTitle` 改为**双字段池**：`title_jpn` 优先，`title` 兜底；任一字段同键即成组。
- `reVersionTokens` 扩充：
  - 版本/语言/汉化类 token **允许方括号或圆括号**（黑名单式，**不剥作品名括号**）；
  - 词表补 `中国翻訳`、`中国語`、`オリジナル`、`AI润色`、含「汉化/漢化」的整块 token；
  - `[DL版]` 整块剥离，并在剥离后**清理空括号残留**（`[ ]`/`()`）。
- 预期：救回 43 组中的 **32 组**（含用户报告的这一组）。
- **不改**「卷号进 key」的隔离设计（实测：这是现有实现避免「上篇/下篇」误合的正确机制，必须保留）。

### 4.2 Tier 2（概率层）

- blocking 实测（3575 本）：同 artist 桶内页数差 ≤5 的候选对 **14,902**；再加「卷号相同 + 核心名 token 交集」后 **12,320** 对。
- 打分成本实测：12,320 对 = **22.9 ms**（Python；每对 1.9 µs，Go 约 1/10~1/30）→ **<1 秒**。
- 人工确认仍走现有忽略机制；low 档折叠展示。
- 阈值与权重**必须用标定集标定**（D9），不拍脑袋定。

### 4.3 交互与工程改造（按 D5/D6）

| 项 | 设计 |
| --- | --- |
| 解耦 | 进维护页 → **立即展示上次持久化的判重结果（秒开、不阻塞）** → 后台检测书库新增/变动 → 增量判重完成后刷新列表；联网核对继续在后台渐进更新 |
| 持久化 | 新增结果表（簇 + 成员 + 判据/置信度 + 生成时间）；重启/换设备不丢，无需重扫 |
| 进度反馈 | `progress` 接口分**两阶段**上报（本地判重 / 联网核对），每阶段带总数与当前序号 |
| 定时任务 | **不做**（D7） |

## 六、忽略表迁移（D8）

- 现状 `ignored_identifiers` 中 10 条 `type=title` 记录的 `title_key` 由**旧清洗算法**产出
  （如 `女神ックス (超次元ゲイム ネプテューヌ) [中国翻訳]`，含未剥离的 `[中国翻訳]`）。
- 升级后需迁移：① 按新算法重算并回填；② 过渡期保留**旧 key 作为副匹配**，避免迁移漏项导致忽略失效。

根因是「括注差异」与「正文差异」被同等对待 —— 前者是元数据（原作名/社团标注增删，如 `(Elsword)` 有无），后者是内容（续篇/加笔，如 `…甘露寺蜜璃` vs `…甘露寺蜜璃 妊娠中`）。
解法：**正文（去括注）相似度作硬门槛 `dedupBodySimMin=0.95`，括注相似度只加分不扣分**（实测正样本正文 1.00、误报样本 0.67~0.80）。

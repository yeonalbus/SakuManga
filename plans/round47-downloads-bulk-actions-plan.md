# Round47：下载列表批量操作（全部取消 / 暂停 / 恢复 / 重试）UI 样稿

> 状态：**样稿已出，待确认 UI 样式；本阶段不改 Vue / Go 代码。**
> 样稿：`plans/mockups/downloads-bulk-actions.html`（自包含 HTML，双击用浏览器打开即可交互）
> 起因：用户要求下载列表支持四个批量按钮，并明确各按钮只在对应状态视图出现；
> 因现有筛选区是一排胶囊按钮、没有承载批量操作的上下文，需要先重排整页信息层级，再施工。
> 本机预览数据：53 条演示任务（画廊 33 / 归档 20），每页 8 条，其中 1 条归档任务为「解压失败」用于演示取消确认的额外警告。

---

## 一、需求与可见性矩阵

| 页签 | 全部暂停 | 全部恢复（resume） | 全部重试 | 全部取消 |
|------|:---:|:---:|:---:|:---:|
| 排队中 | ✓ | — | — | ✓ |
| 下载中 | ✓ | — | — | ✓ |
| 已暂停 | — | ✓ | — | ✓ |
| 出错（error） | — | — | ✓ | ✓ |
| 锁定（error_lock） | — | — | — | ✓ |
| 全部 / 完成 / 已取消 | — | — | — | — |

补充口径：

- 「全部取消」按需求覆盖排队中、下载中、已暂停、出错；`error_lock` 是同一类失败态，样稿也给了「全部取消」，但**不给批量重试**（锁定任务需逐条解锁）。
- 批量操作的作用域是**当前筛选结果的全部任务**（模式 + 状态），跨分页生效，不是只处理当前页。
- 只有「全部取消」需要二次确认；暂停 / 恢复 / 重试直接执行，结果用 toast 汇总。

## 二、UI 方案（样稿）

### 2.1 层级

1. 页头：标题 + 总数 / 活动数量 + 「每 2 秒自动刷新」状态点。
2. 筛选卡：
   - 模式分段控件：全部 / 画廊 / 归档（替代原来的三个胶囊）；
   - 状态页签：全部 / 排队中 / 下载中 / 已暂停 / 出错 / 锁定 / 完成 / 已取消，**每个页签带数量徽标**；
   - 窄屏页签横向滚动，左右渐隐提示还有页签。
3. 上下文批量条（仅在有批量动作且数量 > 0 时出现）：
   - 左侧：状态图标 + 「已暂停任务 12 个 · 全部模式」+ 副标题「跨页生效」；
   - 右侧：主操作（全部恢复 / 全部暂停 / 全部重试）+ 分隔线 + 「全部取消」（红描边）。
   - 执行时整条切换为：spinner + 「正在恢复 12 个任务」+ 进度条 + `3 / 12`；完成后显示 1.5s 结果态。
4. 任务卡片：
   - 左侧状态色条；封面（首字 + 渐变）；
   - 标题右侧状态徽标；其中「出错」信息单独成行（不再挤在 chips 里被截断）；
   - 进度条与底栏：优先级内联按钮 + 单条操作（暂停/恢复/重试/解锁/取消）。
5. 空态：批量操作把当前页签清空后，显示「该筛选下暂无任务」+「查看全部任务」。
6. 确认弹窗：数量、作用域、跨页提示；如果包含解压失败的归档任务，追加一条红色警告（取消会删除损坏压缩包与半解压残留）。

### 2.2 视觉与主题

- 复刻 `App.vue` 的深色 / 浅色变量；样稿顶部提供「浅色预览」切换。
- 状态色：排队灰、下载蓝、暂停琥珀、出错红、锁定橙、完成绿、已取消灰。
- 批量按钮：主操作用实心（暂停/重试蓝、恢复绿），取消用红描边，避免误点。
- 窄屏：批量按钮一行两枚等宽；卡片底栏改为上下两行；优先级/发起者 chip 在窄屏隐藏，保留底栏优先级控件。

## 三、交互状态机

```
点击状态页签
  → 计算该页签的批量按钮组合（见矩阵）
  → 数量为 0 时不渲染批量条，直接显示空态

点击批量主操作（暂停 / 恢复 / 重试）
  → 若 state.bulk 已存在则忽略（防重复）
  → 抓取当前筛选结果中来源状态匹配的任务
  → 进入执行态：逐条更新（施工时改为批量接口一次返回，前端按结果刷新）
  → 完成后 toast 汇总，1.5s 后退出执行态

点击「全部取消」
  → 打开确认弹窗（数量、作用域、损坏压缩包警告）
  → 确认 → 与上面相同；取消 → 关闭弹窗

执行期间
  → 暂停 2s 轮询（避免服务端状态与前端执行态互相抖动）
  → 禁用页签 / 模式切换 / 重复点击
```

施工时的接口建议（样稿不连后端）：

- `GET /api/v1/downloads/stats?mode=`：按当前用户权限聚合 7 个状态的数量 + total。
- `POST /api/v1/downloads/batch-action`：body `{ action, status, mode }`，服务端按筛选条件逐条执行并返回 `{ affected, failed, errors }`；复用现有 `PauseTask / ResumeTask / RetryTask / CancelTask / UnlockTask`，取消时沿用损坏压缩包清理逻辑。
- 或者（不新增批量接口）前端分页拉全量任务 ID 后限并发逐条调用；任务量大时不推荐。

## 四、待用户确认的问题

1. **命名**：需求清单写「全部重启」，规则 3 写「全部恢复」；样稿用「全部恢复」。是否改成「全部重启」？
2. **锁定页签**：保留独立页签，只给「全部取消」；是否还要「全部解锁」？
3. **「全部」页签**：样稿不显示批量入口（混合状态易误操作）；是否要快捷入口，如「暂停下载中 4 / 恢复已暂停 12」？
4. **二次确认**：只对「全部取消」确认；「全部重试」量大时是否也要确认？
5. **作用域**：跨页作用于当前筛选结果的全部任务，确认吗？
6. **按钮数量**：数量在批量条标题里，按钮本身不重复；是否要写成「全部暂停 (9)」？
7. **窄屏位置**：当前批量条在页签下方随页面滚动；是否要在窄屏改成吸附底部？
8. **出错与锁定**：是否合并为一个「出错」页签？合并会让「全部重试」的数量口径变复杂（锁定任务不可重试）。

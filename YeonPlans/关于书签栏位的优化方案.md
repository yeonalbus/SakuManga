## 设计

### 功能

#### 更新开关

用户在哪用到它：
- 建立书签时进行配置
- 在书签页面对书签项管理的时候进行配置

要看到什么：
- 一个开关按钮/勾选项（样式等UI设计再定）

要能做什么：
- 用于调控**更新探测**，当打开这个开关后，开启更新检测功能；关闭这个开关后，则关闭更新检测功能

#### 更新探测

用户在哪用到它：
- 每日自动执行
- 书签页面手动执行

要看到什么：
- 在打开了更新开关的书签名片项上显示对应标记
- 在书签页面显示“检查更新”按钮

要能做什么：
- 在点击/自动执行后，对开启了更新开关的**书签**各发 1 次列表请求
- 判据：通过时间戳 `列表首条 postedAt > 书签.anchor.postedAt`
	- 注意，在用户创建新的书签，或是进行了书签转移后，其更新标记都会被强制清除。

#### **置顶**：

用户在哪用到它：
- 在书签页面对书签项管理的时候进行配置

要看到什么：
- 一个勾选按钮

 要能做什么：
 - 书签项可置顶/取消置顶；
 - 侧栏只常驻置顶书签，上限 5；置顶为空时给引导文案。

#### 书签标记预设

用户在哪用到它：
- 建立书签时进行配置
- 在书签页面对书签项管理的时候进行配置

要看到什么：
- 三个单选项：`newest`（追新锚点）/ `oldest`（续扫锚点）/ `interest`（仅感兴趣）

 要能做什么：
- 选择了单选项后，会在书签项上进行对应显示（显示方式等UI视觉方案）
- 用于让用户知道这个锚点是用来标记什么的

#### 已囤货标记

用户在哪用到它：
- 建立书签时进行配置
- 在书签页面对书签项管理的时候进行配置

要看到什么：
- 一个勾选项（名称待定，我认为”已下载完“存在歧义）

要能做什么：
- 在书签项上显示，用于显式确认"该 tag 已做过无差别下载→筛选"，带确认时间与当时基线作证据；
- 属于**书签项**——每条书签独立设置、独立显示，不需要与其他书签共享。

#### 备注
用户在哪用到它：
- 建立书签时进行配置
- 在书签页面对书签项管理的时候进行配置

要看到什么：
- 一个显示区域以及对应的修改按钮。并且显示区域的字符数输入上限为40个中文字符

要能做什么：
- 用户可以输入自己想要备注的内容

#### 锚点转移更新

用户在哪用到它：
- 建立书签时提醒

要看到什么：
- 一个提示框：提醒用户已存在相同配置的书签，是否需要进行转移

要能做什么：
- 配置书签的时候，检索是否存在「检索条件相同 + 书签标记相同」的书签
	- 判据：比较「规范化后的 keyword tokens + `language` + `onlyRemoved`」，不比对书签标题（位置字段不含 onlyRemoved 等筛选，首页与删除页的标题会重名）
	- 这个判据只是一次比较动作，不建表、不落库
- 如果存在，则提醒用户是否需要替换。替换指的是直接将原书签的标记点位和封面更换成当前的书签所标记的画廊，其余的配置项则不变

#### 锚点缺失优化

用户在哪用到它：
- 当书签锚点跳转发现缺失后，重新定位锚点

要看到什么：
- 提示用户锚点丢失，重新定位

要能做什么（优化&修改）：
- 修改前方案是：提示用户锚点丢失->重新确定锚点->替换后告知用户刷新界面重新点击书签
- 修改后的方案是：
	- 提示用户锚点丢失->重新确定锚点
	- 此时异步进行以下操作：
		1. 首先按照锚点没丢失时候的步骤，跳转到对应的锚点的位置。只不过这里的锚点换成了新的锚点，旧的锚点丢失了。
		2. 然后修改原本的锚点标记，只更新锚点四元组（gid / token / title / postedAt），书签的备注、标记、开关、置顶与已囤货状态一概不动。
			- 这里的原因是用户此时大概率是准备开始搜刮新的内容，会锚定新的画廊，因此不需要大费周章更新失效锚点
			- 而如果用户没有更新锚点，下次还得找到这个有效的新锚点画廊，因此需要保底
		- 注意，需要先写库成功，再触发重新定位
		- 这样做的好处在于用户不需要重新走一遍定位流程，节省时间和操作量

### UI

> 书签升级成一个独立的页面，不再寄生于侧边栏。但是需要在侧边栏保留快速操作项：置顶书签、更新探测
> 
> 注意，UI方案目前仅做暂定分析，需要等html样板

#### 书签页面

作用：用于管理和显示用户配置的**书签项**

布局：
- 以n行3列的方式显示书签项
- 排序方式采取：名称序 + 有更新的书签排在最前。当新书签被建立的时候自动排好顺序，不需要用户手动排序

#### 书签项

作用：用于显示用户配置的书签锚点

布局：
- 整体分为左右两部分：左侧显示锚点对应的画廊封面；右侧显示相关信息
- 禁止折叠显示的内容（即用户最关心的，不能进二级菜单的）：
	- 书签标题：现在将书签标题**固定**为~~旧方案中的**位置**字段~~「位置字段 + 非默认筛选摘要」，不支持修改
	- 备注：备注需要常驻开辟固定大小的显示框，即便用户不输入任何备注内容。
		- 目的是防止书签项大小不一
	- 画廊封面：以宽:高=3:4的比例显示，可能需要对画廊封面进行裁剪、缩放以适应
		- ~~书签项的画廊封面需要被缓存到本地文件夹，避免每次都请求并下载一遍画廊封面数据~~
			- ~~现在的画廊封面都会先被存储到本地一遍，似乎可以直接调取，但是得复制到专门的缓存文件夹中，避免被自动清理掉~~
			- ~~画廊封面不需要异步进行~~
		- ~~在书签项锚定的画廊被改动的时候，被缓存的封面不会被立刻删除，而是被标记上**待删除**，等到固定时间段执行统一的删除操作。~~
			- ~~异步删除可能会导致本地封面堆积，但是能够有效提升用户使用体验，避免使用卡顿~~
		- 按现在的 GC，书签页打开的频率只要高于 7 天一次，封面就自然保活，**不需要复制、不需要待删除标记**。
			- GC 时查一次"书签当前引用的 coverKey 集合"，命中就跳过；
			- 锚点更新后旧封面不再被引用，下轮 GC 自然回收。
	- 更新提示
	- 书签标记
- 可以折叠显示的内容：
	- 更新提示的修改按钮、书签标记的修改按钮、已囤货标记的修改按钮、置顶显示的修改按钮
	- 已囤货标记
		- 这里解释下为什么已囤货可以被折叠：已囤货这个标记影响的是**我是否需要全部下载一遍这个tag的画廊**的决策，并不会影响用户做出**我需要点击这个书签**的决策
		- 因此这个标记权重不是第一梯队

#### 侧边栏

作用：用于让用户快速操作一些常用的书签

布局：
- 侧边栏显示为：
```
书签
├── 更新探测按钮
├── 置顶书签项1
├── 置顶书签项2
├── 置顶书签项3
├── 置顶书签项4
└── 置顶书签项5
```
- 不要做成折叠式抽屉，直接平铺显示即可
- 书签：点击后进入书签页面；
- 更新探测按钮：点击后手动触发更新探测
- 置顶书签项1-5：上限为5个置顶书签，置顶书签只显示**书签标题**、**书签标记**、**更新提示（如有）**

## 附注：

### 更新时段的问题：

我目前不打算新增更多的设置项，更新时段就和**每日刷新时刻**的配置保持一致，避免每个时段都有乱七八糟的任务要做

书签探测应**只复用 `RefreshHour` 这个数值**，自己起独立调度器；不要复用 `EnableDailyRefresh` 开关，否则关 Tag 刷新会连带静默关掉书签探测。

### 功能剪枝：

现在侧栏书签组有两个按钮：🔍（检测失效，Round35）和 🧹（清理失效）。在更新后取消这两个功能

原因在于
1. 我发现在使用的时候几乎不会用到这两个功能，从程序设计以来的2个月中我从来没点击过。
2. 检测的耗时长，不符合快速使用的需求

因此我认为是过度设计，可以被剪枝。

#### AI建议

删掉两个按钮后，这些会变成没有触发者的死代码，方案里要写清"删什么/留什么"：

| 该删                                                                                      | 该留                                          |
| --------------------------------------------------------------------------------------- | ------------------------------------------- |
| `POST /scrape-bookmarks/check` 接口与 `CheckScrapeBookmarks`、`scanBookmarkVisibility` 及其单测 | 定位失败的**会话级** ⚠️（`markAnchorFailed`，零成本视觉提示） |
| 书签上的 `anchor.invalid` 持久化字段 + UI 的"清理失效"入口                                              | 「锚点缺失 → 时间锚迁移」这条流程（它现在肩负全部失效处理）             |
| 前端 `useBookmarkCheck` 的检测编排（保留其中的迁移函数）                                                  | `migratedFrom`（迁移可追溯）                       |

另外**存量数据**要处理：老书签里可能已经写了 `invalid: true`，剪枝后没人清它 → 建议迁移时一次性清空，否则书签墙上会永远挂着一个无法清除的失效标记。

|类别|决定|

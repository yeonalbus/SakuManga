# Round41：日志监控页性能修复（长时停留卡死）

> 起因：用户长期停留在「设置 → 日志 → 监控（其他类别）」查看 Tag 刷新日志时，浏览器逐渐极其卡顿
> （鼠标延迟极大、关闭按钮无响应、需任务管理器强杀）。实测复现确认：**填满 2000 行后进入滚动阶段的
> 每次轮询都会整表重写 2000 行并强制滚动**，真实 Chrome 下约 1 核持续满载 + 进程内存上涨约 200MB。

## 一、根因定位（已实测）

| # | 位置 | 问题 | 实测证据 |
| --- | --- | --- | --- |
| 1 | `src/components/settings/LogSettings.vue` 监控终端（`:key="i"` + `slice(-2000)`） | 超过 2000 行后每次轮询全体索引位移，Vue 按 index 匹配 → 逐行替换 2000 个节点文本。代价与新增行数无关：**只要有 1 行新行就是 2000 行全量更新** | 有头 Chrome，20 行/秒 × 8 分钟：CPU 累计 16s → 437.6s（≈1.1 核）；**填满 2000 行之前几乎零消耗** |
| 2 | 同文件 `scrollTerminal`（`el.scrollTop = el.scrollHeight`） | 每次新行强制同步布局 + 强制滚动；39000px 内容/360px 视口在高 DPI 下重排+重绘+重新光栅化 | 同上；进程内存 671MB → 峰值 880MB |
| 3 | 同文件 `watch(monitorCategory)` + 首次 `pollLogs`（不带 since） | 进入页面/切换类别即全量拉取当天整个日志文件 | 线上实测一次 **16905 行 / 2,026,018 B** 响应，随后只保留 2000 行（88% 白拉） |
| 4 | `backend/internal/handlers/log.go` `tailFileLines` | 每次轮询 `os.ReadFile` 整个文件 + 对**每一行**（含被 since 过滤的）做 `time.ParseInLocation`，O(文件行数)/秒 | 16905 行时约 6ms（当前可接受，随当天日志增长线性恶化） |

**触发时间线**：Tag 刷新期间 other 日志约 1 行/秒（`EH-WARN` + `EH-DETAIL-DEBUG` 成对，每 2 秒 1 本）
→ 进页面约 17 分钟填满 2000 行 → 此后每秒一次「2000 行全表重写 + 强制滚底」→ 越停越卡。

**排除项**：JS 堆无泄漏（headless 20 行/秒 × 10 分钟：heap 41–53MB 稳定、DOM 2269 稳定、主线程 7.4%）。
所以问题在**渲染路径的实现方式**，不在数据量本身。

## 二、方案与取舍（与用户对齐）

| 议题 | 结论 | 理由 |
| --- | --- | --- |
| 保留行数 | **2000 → 300** | 监控是"看最新动态"，300 行足够；300 行 DOM 的整表更新代价可忽略，无需引入虚拟滚动库 |
| 唯一 key | **前端自增 id**（`{id, ts, text}`） | 索引 key 是整表重写的根因；自增 id 让 Vue 只做尾部增删 |
| 滚动 | **贴底跟随（stick-to-bottom）+ rAF 合并** | 用户往上翻历史时不再被拽回底部；贴底状态在 `scroll` 事件里判定，避免每次渲染后强读 `scrollHeight` 造成强制同步布局 |
| 首屏取数 | **只取尾部 300 行**（`limit` 新参数，不带 since） | 消灭 2MB 级首屏响应；`lastTs` 仍取返回行的最大 ts，后续增量轮询不受影响 |
| 轮询接收上限 | **增量轮询带 `limit=600`** | 安全阀：日志暴增时最多接收 600 行（终端只留 300），避免一次性灌入；代价是极端情况下中间行不显示（终端本就只显示尾部） |
| 轮询间隔 | **保留 1s**（不引入 SSE/WebSocket） | 1s 满足"实时监控"体感；瓶颈在渲染不在请求，改协议收益小、改动面大 |
| 后台节流 | **`visibilitychange` 隐藏时停轮询、恢复时立即拉一次** | 用户切走/最小化时不该继续拉日志 |
| 暂停按钮 | **保持现状**（暂停即停请求） | 线上版本已是 `paused \|\| pollLogs()`，无需改 |
| 后端读法 | **从文件尾部反向分块读**（64KB/块）+ 只解析将返回的行 | 首次 `limit=300` 一次 64KB 读即可满足；增量轮询遇到 `ts <= since` 立即停止；加扫描上限与单行长度保护 |

### 后端 `tailFileLines` 语义（新）

```
GET /logs/tail?category=other&since=<ms>&limit=<n>
  limit > 0  → 最多返回最后 limit 行
  limit <= 0 → 兼容旧行为，返回全部命中行（受 tailMaxLines=5000 硬上限约束）
  since > 0  → 只返回 ts > since 的行（时间戳单调 → 命中 ts <= since 即停止反向扫描）
```

- 硬上限 `tailMaxLines = 5000`、扫描上限 `tailMaxScanBytes = 8MB`、块大小 `tailReadChunk = 64KB`。
- `ts = 0`（解析失败行，如多行堆栈）不参与"停止扫描"判定，但 `since > 0` 时仍被过滤（与旧行为一致）。
- 旧前端（线上 bundle）不带 `limit` → 首次返回最后 5000 行而非全文件，**行为兼容且更省**。

## 五、实测验证结果（2026-09-18）

压测方式：`Test/pw-bug/mock-log-server.mjs`（serve `dist/` + 自造日志流，其余 API 代理线上），
`diag-log-verify.mjs` 14 项断言全绿；有头对比用 `diag-log-stream.mjs`（HEADED=1）+ `diag-chrome-rss.ps1` 采样进程树 CPU/内存。

| 指标 | 修复前 | 修复后 | 改善 |
| --- | --- | --- | --- |
| 首屏/切类别 tail 响应体 | 2,026,018 B（16905 行） | 35,711 B（300 行） | **56×** |
| 终端行数（长时停留） | 2000（滚动阶段每轮整表重写） | 300 恒定 | — |
| DOM 节点 | 2269 | 569 | 4× |
| 有头 Chrome CPU（20 行/秒滚动阶段） | ≈1.4 核 | ≈0.15 核 | **≈9×** |
| 有头 Chrome 进程内存 | 671MB → 880MB（+209MB） | 739MB → 653MB（无增长） | — |
| headless 主线程占比（20 行/秒） | 7.4% | 3.14% | 2.4× |
| headless 主线程占比（1 行/秒） | — | 3.08% | 与速率无关（成本由每秒一次渲染+滚动决定） |
| 长任务累计 | 2893ms / 10 分钟 | 188ms / 3 分钟（均在启动阶段） | — |

| 后端 tail 增量轮询（同上） | 1178 µs / 1230 KB alloc | 349 µs / 79 KB alloc | 3.4× / 15.6× |

回归中额外修掉一处隐患：内容增删时浏览器的**滚动锚定**会改写 `scrollTop`，被旧的「是否贴底」判定
误判为"用户翻历史"从而中断自动跟随（高速率采样时复现到距底 384px）。现改为
「只有 600ms 内发生过 wheel/touchmove 用户输入才解除跟随」+ 终端容器 `overflow-anchor: none`，
高速率全程贴底（最大距底 0px）。

> 部署提示：前端改动需重新 `npm run build-only` 并同步 `backend/webui/dist`；后端改动需重新编译 exe。

## 一、总体思路（珱垣确认）

**O3 负责「召回」，O2 负责「决策 + 记忆」，自动删除只留给强证据。**

- 确定性重复（同 GID / 归档 hash / 文件夹内容签名）：维持现状，只出建议，不自动修改。
- 疑似重复（名称级，O3 新增规则 5）：只出建议，**永远不自动删、不自动忽略**，且**不在设置里提供"允许自动修改"的选项**（确定性重复若未来要加自动清理，必须在设置里显式确认开启；本方案不引入该开关）。
- O2 忽略标记：只作用于**疑似重复判定**（+ 规则 3 父子画廊例外，见待确认项 A），确定性重复（规则 1/2/4）与更新检测不参与忽略。

## 三、性能根因（已坐实，代码证据）

3305 本维护/更新慢的根因是**在线请求数量 × 固定 1.2s 限流**，非本地计算：

| 路径 | 代码位置 | 问题 |
|------|----------|------|
| 更新检测 A 段 | `offline.go:87-174` | 对每本有 GID 漫画 `FetchGalleryDetail` + 固定 `Sleep(1200ms)`，**无任何增量跳过** → 全量 3305 本 ≈ 1 小时+ |
| 维护查重 3a | `offline.go:891-996` | 在线父子发现同款 1.2s 限流；有 `parent_checked_at` 增量（首次之后较快），但新导入/forceFull 仍全量 |
| 规则 4 签名 | `offline.go:1023-1102` | 首次全量递归 stat 全部图片；快路径（FileHash + mtime）二次运行已生效，非瓶颈 |
| 双处重复请求 | 更新检测 A 段 vs 维护查重 3a | 对同一 gid 的详情页在两条流程中**重复抓取**，白费请求 |

另：⑨ 移除「进入维护页自动扫描」后，意外全量触发消失，体感慢的问题大头已解。

## 四、方案细化

### 4.1 O2 忽略标记

**数据模型**：后端新增 `ignored_identifiers` 表（放后端，PWA/桌面多端一致）：

```go
type IgnoredIdentifier struct {
    ID        string    // 主键 UUID
    Type      string    // title | gid
    TitleKey  string    // type=title 时：归一化核心名
    Artist    string    // type=title 时：共同画师（来自 OnlineTags 的 artist:xxx），防撞名
    GID       string    // type=gid 时：被忽略的父画廊 gid（规则 3 例外）
    Note      string    // 用户备注（可选）
    CreatedAt time.Time
}
```

**API**：
- `POST /offline/ignore`（创建忽略条目）
- `GET /offline/ignore/list`（忽略清单，供管理页）
- `POST /offline/ignore/:id/restore`（恢复 → 下次查重重新参与）

**忽略清单管理（快速查找/恢复位置，珱垣确认需求）**：
- **入口**：维护页按钮区「🕶️ 忽略清单 (N)」（N = 当前忽略条目数）；全量查重的「已忽略」折叠区亦提供「管理忽略清单」跳转。
- **形态**：弹层（modal，参照项目内 `BookshelfPickerOverlay` 浮层模式，不新增路由）。
- **内容**（按类型分组展示，每条含）：
  - title 型：识别名（归一化核心名 + 画师）· 忽略时间 · 覆盖的本地条目数（查重时统计，帮助判断恢复影响范围）· 「恢复」按钮；
  - gid 型：父画廊标题（附 gid）· 忽略时间 · 「恢复」按钮。
- **恢复交互**：点击「恢复」→ 删除该忽略条目 → toast「已恢复，下次查重重新参与」→ 计数即时更新；无需二次确认（轻量操作）。
- **空态**：「暂无忽略条目」提示。
- **联动**：全量查重结果中「已忽略」条目可单独解除忽略（等价于恢复对应条目），与清单管理双通道。

**作用域与过滤**：
- 增量查重：命中忽略的疑似重复组直接跳过（title 型：TitleKey+Artist 双匹配；gid 型：父 gid 匹配规则 3 建议删除项）。
- 全量查重（forceFull）：**不豁免**，仍扫描并展示，但带「已忽略」徽标、默认折叠、不参与批量勾选，可单独解除忽略。
- 规则 1/2/4（同 GID/hash/签名）：完全不读取忽略表。
- 更新检测：不读取忽略表（v1 不做更新忽略入口，表结构已预留，后续可开）。

**父子继承交互**：忽略一个条目时，前端预览「该作品的关联画廊（同核心名 + 父子链）将一并忽略」并让用户确认范围；不做静默隐式传播。

### 4.2 O3 查重逻辑增强（新增规则 5：疑似重复）

**定位**：纯本地、纯建议的弱证据规则，产出「疑似重复组」；与规则 1/2/3/4 的强证据互不干扰。

**分层实现（各层独立可测）**：

1. **清洗层**（纯函数）：
   - 剥离版本后缀：`(C94)`、`Vol.3`、`第2話`、`後編/前編/下巻/上巻`、`DL版`、汉化组前缀 → 提取「核心名」；
   - **方括号前缀分路处理**：画师/社团（如 `[milky]`）→ 提取为画师特征参与比对（**不剥离**）；汉化组/版本标记 → 才剥离；
   - **卷号提取为独立特征**（不纯剥离）：核心名相同 + 卷号不同 = 续集/分卷，**判为不同**；
   - 罗马数字 → 阿拉伯数字归一；全角/半角、大小写归一。
2. **判定层**：按「核心名 + 画师」预分组（组内才比对，O(n) 分组 + 组内小规模比对）；组内两两计算相似度 + 页数容差：
   - 页数用 `OriginalPageCount`（物理页数，隐藏页功能影响）；
   - **双向不对称页数规则**：页数差 ≤5 为「同」的强支持信号；页数差 >5 只降置信度、不硬性判异（重绘版/英化双页合并会页数差大）。
3. **决策层**（阈值可配置）：
   - 高置信（核心名相同 + 画师相同 + 页数差 ≤5 + 无卷号差异）→ 自动归入「疑似重复组」；
   - 中置信 → 弹窗人工确认；
   - 低置信 → 静默。
   - 误判代价为零（只多一条提示 + 一次点击忽略），故无自动删除风险。

**输出结构（簇，鲸娘设计）**：

```go
type DedupCluster struct {
    ID         string           // 簇 ID
    TitleKey   string           // 归一化核心名
    Artist     string           // 共同画师
    Confidence string           // high | medium（决策层输出）
    Reason     string           // 判定依据摘要（如"画师相同 + 页数差 2 页"）
    Members    []ClusterMember  // 成员（≥2）
    Ignored    bool             // 是否已命中忽略（全量扫描时展示用）
}
type ClusterMember struct {
    Comic      models.OfflineComic
    PageCount  int    // 物理页数
    Lang       string // 语言（从 tags 提取 language:xxx）
}
```

前端：每个疑似重复组 = 一张卡片（组标题=核心名，成员缩略图横排，页数/画师/语言标签，置信度徽标；操作：忽略本组 / 查看成员对比）。后端 `maintain/result` 返回新增 `clusters` 字段，与现有 `items`（强证据建议）并存。

### 4.3 性能优化（3305 本基线）

| 项 | 方案 | 收益 | 实施状态 |
|----|------|------|----------|
| A. 自适应限流 | 抽公共限流器：初始 800ms，连续 5 次成功降至下限 500ms（≈2 req/s）；失败/429/503 退避 ×2 封顶 5s。替换 offline.go 全部 7 处固定 1.2s | 全量检测 ~1h+ → ~35min | ✅ 已实施（`eh_ratelimit.go` EHRateLimiter；更新检测/老化判定/维护 3a/GID 回填全覆盖） |
| B. 详情缓存复用 | 更新检测 A 段与维护查重 3a 对同 gid 的 `FetchGalleryDetail` 结果共享进程内存缓存 | 白省约一半在线请求 | ⏸ 暂缓（决策 C1）：跨任务缓存引入「E 站详情已变化但缓存未过期」的陈旧数据风险；收益仅在「短时间连续跑两个全量」场景，日常「维护增量 + 更新全量」收益低 |
| C. 增量窗口 | 维护查重 3a `parent_checked_at` 改窗口内跳过；更新检测新增 LastCheckedAt 窗口 | 日常增量维护秒级完成 | ⏸ 暂缓（决策 C2）：3a 现状「永不重查 + forceFull 兜底」在频繁增量场景最快；改 24h 窗口会让「每天跑维护」的用户每天全量联网（反而更慢）。已核对项增量本就跳过，⑨ 已消除意外全量触发 |
| D. O2 联动 | 增量扫描命中忽略的 title/gid 直接跳过，不发请求 | 忽略即加速 | ✅ 已实施（规则 3 gid 忽略在联网前拦截；title 簇忽略在簇生成时跳过） |
| E. 并发（可选） | 设置里进阶项：并发 1（默认）/ 2 / 3，标注 E 站限流风险 | 进一步加速，默认关 | 未实施（后续排期） |

O3 名称比对为纯本地 CPU，预分组后组大小通常 1~3，不构成瓶颈。

> **决策 C1/C2（鲸娘实施中判断，需珱垣确认）**：性能 B/C 暂缓，理由见上表。若珱垣希望保留「更新检测间隔」能力，可后续做成设置项（默认 7 天窗口），单独排期。

### 4.4 ⑨ 去掉自动扫描

`OfflineMaintain.vue` 移除「检测到书库变更 → 进入页面自动启动增量查重」逻辑（约 L314-336），改为：检测到变更 → 仅置 `resultStale=true` → 页面显示过期 banner（「查重结果已过期，请点击重新扫描」），扫描仅由手动按钮触发。
